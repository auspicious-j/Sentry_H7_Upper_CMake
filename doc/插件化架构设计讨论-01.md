# 插件化架构设计讨论记录（第 1 轮）

日期：2026-10-08  
状态：持续更新；已确认决策与待确认问题分开记录。最近更新：2026-10-09。设计目标不等于当前代码已全部实现。

## 目标

搭建可组合、可裁剪、可替换的 C++ 插件框架，通过薄适配层接入现有底盘、云台、通信、电机、裁判系统、视觉等业务。优先保留团队原有 C 算法、参数与状态机，不以重写业务为迁移手段。新增机械臂等功能时，只增加自己的节点、端口和组装配置。

插件可以继续拥有内部图和内部节点。节点之间可以形成多起点、多终点和交叉连接的有向图。

## 已确认的基础约束

### 当前实现与验证范围

- 当前只实现 STM32 + FreeRTOS，Linux/NUC 是后续移植目标。
- 当前不实现 Linux 后端、PC 仿真、主机测试工程或测试运行器。
- 保持业务与平台分离，为后续移植保留接口边界。
- 最新约定（2026-10-09）：助手连续推进并自行做可用的静态/目标编译器检查，不再要求用户逐板块 Keil 编译确认；烧录和实车观察仍由用户执行。
- 旧源码和旧硬件输出链路保持原样；新组件拥有独立状态，只通过明确的输入快照交接。最终对比应区分输入/计算步数未对齐与数值不一致。
- 旧链路保留硬件输出权；新框架先提供调试结果，不重复启动外设或发送控制命令。
- 不重复调用修改全局状态的旧业务函数。只有具备独立状态实例的算法才能独立旁路运行；否则观察原函数一次执行的结果。
- 接管和删除旧代码前确认新链路不再依赖待删除实现；代码审查或编译通过不等于实车通过。

### CubeMX

- 不修改 `.ioc` 和 CubeMX 外设配置。
- 不重构 `Core/`、`Drivers/`、`USB_DEVICE/`、`Middlewares/` 等生成部分。
- 业务 C++ 代码放在独立目录，通过适配层调用 HAL 和 FreeRTOS。
- CubeMX 重新生成后，业务代码应继续保留并可重新接入。
- `main.c`、`freertos.c` 等 CubeMX 生成文件保持 C，不改为 `.cpp`。
- C++ 通过 `extern "C"` 薄桥接从 CubeMX 的 `USER CODE` 区域进入。
- 新框架和适配器使用 `.cpp`；原有业务文件可以继续是 C，不强制改名或重写。需要拆分旧函数的副作用时，先说明必要的最小改动。

### C++

- 使用 C++17。
- 框架核心及 STM32 侧关闭异常和 RTTI；未来 Linux 第三方库采用独立构建边界，接口使用状态码，不将第三方异常传播到核心。
- 使用类、接口、虚函数、模板、`constexpr`、RAII 和强类型枚举。
- 框架核心及 STM32 侧优先使用静态内存和固定容量容器；未来 ROS 2 / 推理库的资源由对应后端管理，不承诺整个 Linux 进程无动态分配。
- 不使用 `new/delete` 作为业务模块的常规生命周期管理方式。

### 编译期裁剪与启动期组装

```text
编译期裁剪：决定插件代码是否进入固件。
启动期组装：决定已编译插件是否注册、连接和运行。
```

STM32 和 NUC/Linux 共用一份独立的编译配置头文件，例如 `Config/robot_build_config.h`。它定义插件编译开关、基础帧率、图容量、性能统计和调试快照开关。第一版不引入 Flash/JSON 启动配置；启动时根据同一份编译配置组装插件图。需要类型和单位检查的业务参数使用 C++ `constexpr` 配置，而不是全部使用宏。

## 插件节点模型

所有层级使用同一个插件节点协议，不区分“一级插件”“子插件”“叶子插件”三套类型。

每个节点都可以拥有自己的内部插件图：

- 内部图为空时，节点直接完成一段业务逻辑。
- 内部图不为空时，节点可以继续连接和组织更多节点。
- 节点可以同时连接外部图和内部图。
- 启动时各层级图展开成统一执行计划，运行时保留路径用于调试。

```text
RobotNode
├── ChassisNode
│   ├── InputNode
│   ├── KinematicsNode
│   ├── PowerLimiterNode
│   ├── WheelControllerNode × 4
│   └── OfflineDetectNode
├── GimbalNode
└── ArmNode
```

这只是组织和调试视图，实际依赖关系由有向图边决定，因此允许多起点、多终点和交叉连接。

对象所有权与执行依赖分开：父节点可以持有固定成员，形成稳定的对象组合关系；`PluginGraph` 单独记录执行和数据连接，因此执行关系仍然可以是网状的。节点通过 `compose()` 注册自己的内部节点和连接，根组装器负责连接跨节点端口。

节点存储和允许的连接在启动期组装并冻结；运行期可选择预定义分支，也可切换已验证的执行计划。不进行任意新增、删除、重连或临时拓扑排序。节点禁用、故障与分支未选中是不同原因，不应混为同一种故障。

节点和端口连接由 C++ `compose()` 代码声明，启动时依次执行 `compose`、`validate`、`compile`、`freeze`。宏配置只控制节点是否编译和注册，不隐藏具体连接关系。验证通过后生成固定容量执行计划；需要不同顺序时提前生成多套计划，运行时切换计划而不重新拓扑排序。每套可激活计划分别验证依赖与环，不能把互斥计划简单并成一张图执行。

迁移以框架能力为主：先完善节点、端口、执行计划和观察能力，再通过薄适配层接入旧业务。已完成的电机与底盘反馈观察继续保留，暂停重新实现底盘解算的方向。后续重点是条件分支、预验证计划切换和外部数据/计算后端接口。

## 图连接

```text
数据边：A.output → B.input
顺序边：A 必须先于 B，但不传递数据
延迟边：A.output → B.input，使用上一周期数据
```

延迟边用于反馈回路，避免同一周期形成非法环。启动时验证节点 ID、端口连接、类型和单位、单写者规则、非延迟环以及固定容量限制。

## 端口与数据类型

端口使用强类型协议：

```cpp
Port<ChassisCommand>
Port<MotorFeedback>
Port<MotionConstraint>
Port<MotorCommand>
```

必要时把单位写入类型，例如 `LinearVelocityMps`、`AngleDegree`。规则是：一个输出单写、允许多读；输入必须连接或明确可选；不使用统一字节缓冲区隐藏类型。

底盘依赖通用的 `MotionConstraint`，不直接依赖 `ArmNode`、`JudgeNode` 或 `BatteryNode`。这些模块都可以提供同一种约束。

## 1 kHz 帧模型

全局基础帧率确定为 1 kHz。端口信号每 1 ms 都有可读取值；节点业务逻辑可以按整数倍降频：

```text
1 kHz：每帧执行
500 Hz：每 2 帧执行
100 Hz：每 10 帧执行
50 Hz：每 20 帧执行
```

必须区分信号帧率和业务帧率。低频节点在未重新计算期间保持上一份有效输出，后面连接普通的速率适配或滤波节点：

```text
低频算法节点 → RateTransition/SlewFilter（1 kHz）→ 高速输出节点
```

可复用滤波节点包括零阶保持、线性插值、限斜率和低通；急停等安全信号不能使用会延迟响应的普通滤波策略。

## 帧数据可见性

不采用所有节点统一下一帧才可见的纯双缓冲，因为这会给每条内部边隐含增加一帧延迟。

采用混合语义：

```text
外部输入：帧边界双缓冲，避免 ISR/DMA 数据撕裂。
图内部连接：同帧提交，按依赖顺序传递。
中断/DMA：由平台适配层双缓冲或短临界区保护。
```

节点 A 提交 frame N 后，依赖节点 B 可以在同一个 frame N 读取 A 的输出；并行分支汇合时，后继节点等待当前帧所有前置节点提交。

## FreeRTOS 与插件职责

```text
插件：业务、端口、依赖和状态。
插件图：业务数据流和执行依赖。
PluginExecutor：生成执行计划并分配执行域。
FreeRTOS：任务、并行、等待、优先级和时间片。
平台适配层：HAL、ISR、DMA、队列和通知。
```

插件不直接调用 `xTaskCreate`、`vTaskDelay`、`xQueueSend`。执行域包括：

```text
ControlDomain：1 kHz 底盘、云台和电机控制
IoDomain：CAN、UART、USB、DMA 适配
CommunicationDomain：遥控、视觉、裁判协议
SupervisorDomain：离线检测、故障和参数管理
WorkerDomain：日志、诊断和复杂后台计算
```

同一执行域内部按图顺序执行；跨执行域使用 `FramePort`、任务通知、固定容量队列和 DMA 回调。

当前执行后端仅实现 STM32 + FreeRTOS。未来移植到 NUC/Linux 时通过替换平台与执行后端复用业务插件；Linux 线程实现和 PC 仿真不属于当前交付范围。

## 性能测量

性能系统作为一级基础服务，抽象为 `IClock` 和 `IProfiler`：

```text
STM32：DWT/CYCCNT 或高精度定时器
Linux（未来候选，当前不实现）：clock_gettime(CLOCK_MONOTONIC_RAW)
```

执行器自动测量每个节点耗时；插件内部用 RAII 探针进行细分，例如：

```cpp
PERF_SCOPE("chassis.kinematics.inverse");
```

支持统计模式和追踪模式。统计模式记录计数、平均、最小、最大、P95/P99 和超预算次数；追踪模式使用固定容量环形缓冲区记录节点、帧号、任务和时间线。节点可声明耗时预算，统计整帧耗时、周期抖动、CPU 占用、任务等待、队列满和丢帧情况。

## 故障与生命周期

```text
Created → Configured → Running → Degraded/Faulted → Stopped
```

业务处理不抛异常，使用状态码。故障策略包括：

```text
Required：失败后停止相关执行域
Isolated：节点停止，其他节点继续
Fallback：切换备用输入或算法
MonitorOnly：只记录故障，不影响控制
```

启动阶段验证配置、端口、依赖、循环、周期和资源。后继节点根据输入有效性选择使用上一有效值、进入安全输出、切换备用路径或停止自身。

## 2026-10-09 确认：旧业务保留、ROS 2 / 模型边界与条件执行

本节为已确认的设计方向，尚未宣称条件调度、ROS 2 或模型后端已经实现。

### 条件分支与执行计划

- 各条路线在编写组装代码时已知；运行时根据条件激活路线。
- 一个分支可包含完整子图，内部节点仍使用统一接口并可继续嵌套。
- 汇合处只等待本轮选中分支；未选中分支标记为跳过，不能无限等待或误用它上次的输出。
- 同一执行计划内共享节点每帧只执行一次。
- 不同执行顺序预先生成并验证为不同计划，每个计划必须满足自身数据依赖。
- 路径切换在受控帧边界生效；跨任务还需确认上一轮执行已经完成，不能仅修改一个全局布尔值。
- 为路径提供进入/退出/状态重置接口；PID 积分、滤波历史与模型隐藏状态是否保留由业务适配声明。
- 异步请求记录请求号、输入时间和路径版本；旧路径迟到的结果不能进入新路径输出。
- 增加路径 ID、分支执行/跳过次数、切换次数及耗时观测。
- 任意运行时改图暂不纳入当前范围。

### ROS 2 接入边界（未来上位机）

ROS 2 桥接节点负责消息类型转换和发布/订阅；框架业务节点不继承 rclcpp::Node、不依赖 ROS 消息类型。ROS 回调与插件执行器通过明确的异步交接存储连接，不能并发调用同一业务实例。

接口应区分最新值与事件队列，并携带有效性、数据序号、时间来源和过期策略。ROS 时间与本机单调时间不能直接混算；QoS、Topic 和线程配置由平台桥接负责。STM32 不编译或链接 ROS 依赖。

### 强化学习与推理后端（未来上位机）

采用“业务输入 → 观测构造 → 推理后端 → 动作解释 → 业务输出”。ONNX Runtime 与 RKNN 是不同后端，不将模型文件后缀作为可互换的依据。

模型能替换哪个节点或子图由输入输出语义决定：单位、坐标系、轮序、归一化、历史窗口、动作缩放均明确；力矩输出不能直接替代速度/舵角输出。为推理预留非阻塞提交、结果查询、超时、请求编号、路径版本、结果年龄和重置接口。

控制基础帧率保持 1 kHz 的目标，模型业务频率可以更低。滤波不会提高真实推理频率或刷新原始输入/结果时间。第三方线程和内存资源归推理后端管理，模型加载/预热与正常控制执行分开。

### 后续实施顺序

先实现 STM32 可用的预定义条件分支及可观察状态；再完善多计划切换和异步结果生命周期。当前只预留 ROS 2 / ONNX / RKNN 边界，不引入 Linux 后端或仿真工程。原定逐板块确认流程已被上方最新用户约定替代，不再等待用户重复确认编译。

## 2026-10-09 实施进展：多套预验证执行计划

扩展 PluginGraph，为固定节点集合按计划分别验证依赖与拓扑排序。公共边全计划生效，专属边只在对应计划生效；不同计划可声明相反顺序。

新增两个无硬件顺序探针，Debug 通过本帧执行序号验证 A→B/B→A，次数随执行增长不因切换清零。分支选择与计划选择保持独立。
本板块不改变端口连接、业务公式、PID 状态或 CubeMX；configure/start/stop 固定采用计划0初始化顺序，切换通过 onEnter/onExit/onPlanChanged 扩展，默认不自动重置业务状态。

## 2026-10-09 实施进展：节点路径生命周期通知

在 PluginNode 增加 onEnter/onExit/onPlanChanged 默认空回调。执行器在帧边界锁存路线和计划，计算自身与祖先状态均可运行的激活集合；旧激活节点逆序退出，新激活节点顺序进入，继续激活节点仅在计划改变时收到计划通知。
