# 插件化架构设计讨论记录（第 1 轮）

日期：2026-10-08  
状态：讨论中；已确认决策与待确认问题分开记录。

## 目标

把底盘、云台、通信、电机、裁判系统、视觉等业务改造成可组合、可裁剪、可替换的 C++ 插件图。新增机械臂等功能时，只增加它自己的节点、端口和组装配置，已有业务不因新增模块而修改。

插件可以继续拥有内部图和内部节点。节点之间可以形成多起点、多终点和交叉连接的有向图。

## 已确认的基础约束

### 当前实现与验证范围

- 当前只实现 STM32 + FreeRTOS，Linux/NUC 是后续移植目标。
- 当前不实现 Linux 后端、PC 仿真、主机测试工程或测试运行器。
- 保持业务与平台分离，为后续移植保留接口边界。
- 编译、烧录和实车测试由用户执行；助手负责代码修改、静态检查、调试观测项说明以及根据实车反馈修正。
- 按已确认的渐进迁移顺序逐阶段交付，保留旧/新实现切换和回退能力。代码审查不等于编译或实车验证通过。

### CubeMX

- 不修改 `.ioc` 和 CubeMX 外设配置。
- 不重构 `Core/`、`Drivers/`、`USB_DEVICE/`、`Middlewares/` 等生成部分。
- 业务 C++ 代码放在独立目录，通过适配层调用 HAL 和 FreeRTOS。
- CubeMX 重新生成后，业务代码应继续保留并可重新接入。
- `main.c`、`freertos.c` 等 CubeMX 生成文件保持 C，不改为 `.cpp`。
- C++ 通过 `extern "C"` 薄桥接从 CubeMX 的 `USER CODE` 区域进入。
- 用户业务文件可以逐步迁移为 `.cpp`，不要求一次性改名全部现有文件。

### C++

- 使用 C++17。
- 关闭异常和 RTTI。
- 使用类、接口、虚函数、模板、`constexpr`、RAII 和强类型枚举。
- 业务对象优先使用静态内存和固定容量容器。
- 不使用 `new/delete` 作为业务模块的常规生命周期管理方式。

### 编译期裁剪与启动期组装

```text
编译期裁剪：决定插件代码是否进入固件。
启动期组装：决定已编译插件是否注册、连接和运行。
```

STM32 和 NUC/Linux 共用一份独立的编译配置头文件，例如 `Config/robot_build_config.h`。它定义插件编译开关、基础帧率、图容量、性能统计和调试快照开关。第一版不引入 Flash/JSON 启动配置；启动时根据同一份编译配置组装插件图。需要类型和单位检查的业务参数使用 C++ `constexpr` 配置，而不是全部使用宏。

## 插件节点模型

所有层级使用同一个插件节点协议，不区分“一级插件”“子插件”“叶子插件”三套类型。

每个节点都可以拥有自己的内部插件图：

- 内部图为空时，节点直接完成一段业务逻辑。
- 内部图不为空时，节点可以继续连接和组织更多节点。
- 节点可以同时连接外部图和内部图。
- 启动时各层级图展开成统一执行计划，运行时保留路径用于调试。

```text
RobotNode
├── ChassisNode
│   ├── InputNode
│   ├── KinematicsNode
│   ├── PowerLimiterNode
│   ├── WheelControllerNode × 4
│   └── OfflineDetectNode
├── GimbalNode
└── ArmNode
```

这只是组织和调试视图，实际依赖关系由有向图边决定，因此允许多起点、多终点和交叉连接。

对象所有权与执行依赖分开：父节点可以持有固定成员，形成稳定的对象组合关系；`PluginGraph` 单独记录执行和数据连接，因此执行关系仍然可以是网状的。节点通过 `compose()` 注册自己的内部节点和连接，根组装器负责连接跨节点端口。

插件图在启动期组装和验证，运行期冻结。运行期不增删节点、不重建端口连接和执行计划；需要停用功能时将节点置为 `Disabled` 或故障状态，并输出无效值或安全值。这样可以保持静态内存、实时性、任务同步和性能统计 ID 的稳定。

节点和端口连接由 C++ `compose()` 代码声明，启动时依次执行 `compose`、`validate`、`compile`、`freeze`。宏配置只控制节点是否编译和注册，不隐藏具体连接关系。验证通过后生成固定容量执行计划，运行时不重新拓扑排序。

迁移采用“先架子、再一条完整链路、最后扩展”的方式：先建立 C++ 编译和 C 桥接，再建立平台服务，然后迁移电机/CAN 适配，接着以底盘完成 `CAN feedback → MotorFeedbackNode → ChassisNode → PowerLimiterNode → MotorOutputNode → CAN transmit` 链路，之后逐个迁移云台、射击、通信、诊断和调试。迁移期间保留旧/新实现切换开关，支持逐帧比较和回退。

## 图连接

```text
数据边：A.output → B.input
顺序边：A 必须先于 B，但不传递数据
延迟边：A.output → B.input，使用上一周期数据
```

延迟边用于反馈回路，避免同一周期形成非法环。启动时验证节点 ID、端口连接、类型和单位、单写者规则、非延迟环以及固定容量限制。

## 端口与数据类型

端口使用强类型协议：

```cpp
Port<ChassisCommand>
Port<MotorFeedback>
Port<MotionConstraint>
Port<MotorCommand>
```

必要时把单位写入类型，例如 `LinearVelocityMps`、`AngleDegree`。规则是：一个输出单写、允许多读；输入必须连接或明确可选；不使用统一字节缓冲区隐藏类型。

底盘依赖通用的 `MotionConstraint`，不直接依赖 `ArmNode`、`JudgeNode` 或 `BatteryNode`。这些模块都可以提供同一种约束。

## 1 kHz 帧模型

全局基础帧率确定为 1 kHz。端口信号每 1 ms 都有可读取值；节点业务逻辑可以按整数倍降频：

```text
1 kHz：每帧执行
500 Hz：每 2 帧执行
100 Hz：每 10 帧执行
50 Hz：每 20 帧执行
```

必须区分信号帧率和业务帧率。低频节点在未重新计算期间保持上一份有效输出，后面连接普通的速率适配或滤波节点：

```text
低频算法节点 → RateTransition/SlewFilter（1 kHz）→ 高速输出节点
```

可复用滤波节点包括零阶保持、线性插值、限斜率和低通；急停等安全信号不能使用会延迟响应的普通滤波策略。

## 帧数据可见性

不采用所有节点统一下一帧才可见的纯双缓冲，因为这会给每条内部边隐含增加一帧延迟。

采用混合语义：

```text
外部输入：帧边界双缓冲，避免 ISR/DMA 数据撕裂。
图内部连接：同帧提交，按依赖顺序传递。
中断/DMA：由平台适配层双缓冲或短临界区保护。
```

节点 A 提交 frame N 后，依赖节点 B 可以在同一个 frame N 读取 A 的输出；并行分支汇合时，后继节点等待当前帧所有前置节点提交。

## FreeRTOS 与插件职责

```text
插件：业务、端口、依赖和状态。
插件图：业务数据流和执行依赖。
PluginExecutor：生成执行计划并分配执行域。
FreeRTOS：任务、并行、等待、优先级和时间片。
平台适配层：HAL、ISR、DMA、队列和通知。
```

插件不直接调用 `xTaskCreate`、`vTaskDelay`、`xQueueSend`。执行域包括：

```text
ControlDomain：1 kHz 底盘、云台和电机控制
IoDomain：CAN、UART、USB、DMA 适配
CommunicationDomain：遥控、视觉、裁判协议
SupervisorDomain：离线检测、故障和参数管理
WorkerDomain：日志、诊断和复杂后台计算
```

同一执行域内部按图顺序执行；跨执行域使用 `FramePort`、任务通知、固定容量队列和 DMA 回调。

当前执行后端仅实现 STM32 + FreeRTOS。未来移植到 NUC/Linux 时通过替换平台与执行后端复用业务插件；Linux 线程实现和 PC 仿真不属于当前交付范围。

## 性能测量

性能系统作为一级基础服务，抽象为 `IClock` 和 `IProfiler`：

```text
STM32：DWT/CYCCNT 或高精度定时器
Linux（未来候选，当前不实现）：clock_gettime(CLOCK_MONOTONIC_RAW)
```

执行器自动测量每个节点耗时；插件内部用 RAII 探针进行细分，例如：

```cpp
PERF_SCOPE("chassis.kinematics.inverse");
```

支持统计模式和追踪模式。统计模式记录计数、平均、最小、最大、P95/P99 和超预算次数；追踪模式使用固定容量环形缓冲区记录节点、帧号、任务和时间线。节点可声明耗时预算，统计整帧耗时、周期抖动、CPU 占用、任务等待、队列满和丢帧情况。

## 故障与生命周期

```text
Created → Configured → Running → Degraded/Faulted → Stopped
```

业务处理不抛异常，使用状态码。故障策略包括：

```text
Required：失败后停止相关执行域
Isolated：节点停止，其他节点继续
Fallback：切换备用输入或算法
MonitorOnly：只记录故障，不影响控制
```

启动阶段验证配置、端口、依赖、循环、周期和资源。后继节点根据输入有效性选择使用上一有效值、进入安全输出、切换备用路径或停止自身。
